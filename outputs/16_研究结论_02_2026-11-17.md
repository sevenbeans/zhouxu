# 研究结论 02

- 版本日期：2026-11-17
- 证据基础：1 位深访用户、3 轮文字问答，以及 1 次短访谈补充回访
- 样本口径：补充回访暂归入同一用户，不增加独立用户数
- 结论用途：修正 V1 的信息结构和冲突页范围

## 一句话结论

用户需要的不是一份自动生成的日历，而是一份能明确“截止时间、具体动作、紧急程度和当前进度”的未来七天行动计划。

## 本轮新增发现

### 1. 日期不是唯一的事件类型

校招双选会现场递交简历没有截止日期，也不产生后续日历节点。

产品必须区分：

- 明确日期
- 只有发布日期
- 无截止日期
- 现场完成、无需排期

不能把“未找到日期”一律当成识别失败。

### 2. 冲突的核心是缺少比较依据

中国移动和农业银行笔试冲突时，用户凭感觉选择中国移动，至今没有后续消息，也无法判断选择是否合理。

冲突页至少需要展示：

- 公司与岗位
- 流程阶段
- 时间与预计耗时
- 笔试或面试形式
- 岗位职责与地点
- 材料完成状态
- 用户自己的优先级或适配备注

不做自动适配度评分，不替用户选择。

### 3. 七天视图需要行动信息

用户的第一眼信息为：

1. 截止日期
2. 具体任务
3. 紧急程度排序

分类仍保留为“实习、秋招、学校”标签，但不再是首屏唯一组织方式。

### 4. 进度状态是试用成功标准

用户希望明确两项结果：

- 各岗位和任务当前进行到哪里
- 未来一周的完整规划

因此需要一套简单、可手动维护的状态：

```text
待准备 → 已投递 → 笔试 → 面试 → 结果
```

课程和实习任务可以使用：

```text
未开始 → 进行中 → 已完成
```

状态默认由用户确认，AI 不自动认定“已投递”或“已完成”。

## 对 V1 的修正

### 周视图

每条事项至少显示：

- 截止日期和时间
- 具体下一步任务
- 紧急程度
- 分类标签
- 当前状态
- 日期是否已确认

### 冲突页

先并排展示两份岗位或考试上下文，再允许用户选择。至少包含公司、岗位、阶段、时间、考试形式、地点、材料状态和个人备注。

### 录入

截图和粘贴文本继续保留。对于无截止日期或现场完成的事项，增加“无需排期”状态，不生成虚假日期。

### 状态

投递和任务状态必须手动确认。可以生成状态草稿，但不能自动改成“已投递”或“已完成”。

## 仍需验证

1. 紧急程度由剩余天数计算，还是由用户手动标记重要性。
2. 用户是否愿意为每条招聘填写“具体任务”。
3. 冲突比较中最重要的三个岗位字段。
4. 进度状态是否过重，能否缩减为三个状态。
5. 周日晚上是否仍是主要打开时机。
6. 用户是否愿意提供真实笔试通知截图。
7. 用户是否愿意参加两周试用。

## 下一轮访谈的重点

不要继续泛问“你需要什么功能”，改为让用户完成三个具体任务：

1. 从三张招聘截图读出日期状态。
2. 给中国移动和农业银行的冲突信息选择最重要的三项比较字段。
3. 用一个岗位示例走完“待准备 → 已投递 → 笔试 → 面试”的状态。

完成后再判断：

- 周视图是否真的减少混乱
- 具体任务字段是否有人维护
- 冲突比较是否帮助用户做出更有依据的选择
