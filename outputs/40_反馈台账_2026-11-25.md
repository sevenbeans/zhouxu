# 反馈台账（截至 2026-11-25）

- 用途：把每一次真实反馈都变成可追溯的一行，避免"修过但记不清修了什么"
- 冻结状态：2026-11-25 冻结，此后新反馈只入"待处理"区，不改已冻结行
- 覆盖：1 名核心用户 + 2 位外部试用者，共 24 条反馈，全部闭环

## 一、怎么读这张表

每行六列：

| 列 | 含义 |
| --- | --- |
| 编号 | A = 核心用户，B = iPhone 试用者，C = 电脑试用者，D = 外部建议 |
| 反馈 | 尽量保留原话，不做美化 |
| 根因 | 我为什么判断这是真问题，而不是误解 |
| 处理 | 实际改了什么（写清是改 UI、改模型还是改文案） |
| 验证 | 拿哪个测试用例或截图证明改好了 |
| 状态 | 已修 / 已修待感知 / 记入遗留 |

**"已修"和"已修待感知"要分开。** 有些修复用户当场没反应，
说明技术上修好了但没进入他的心智，这跟没修是一个性质的问题，不能混在一起算成功。

## 七、这张表最终变成简历上的什么

**台账本身不会出现在简历上。** 它是证据层，简历上出现的是三层：

### 第一层：一句可核验的概括（简历项目段）

> 依据真实用户反馈组织 5 轮迭代，闭环 24 条问题（识别解析 7 / 语义模型 5 / 交互表达 7 / 平台格式 4 / 决策 1），
> 并将其固化为 195 项自动化回归断言。

这句话里的每个数字都能在本表里找到来源。面试官问"24 条是怎么来的"，我把表打开给他看。

### 第二层：作品集案例页的第四章（`/case/`）

案例页"04 迭代"章节已经把台账里最有价值的两列——**反馈原话**和**根因**——
写成了五轮迭代的叙事。这部分已经上线，不用再改。

### 第三层：面试时能顶住追问的三句话

| 追问 | 用台账里的哪一行回答 |
| --- | --- |
| "你怎么知道改对了？" | 195 项断言，每条反馈都有对应测试用例（验证列） |
| "这个需求是真的还是你想象的？" | D-01 考公那条我**拒绝了**做板块；C-01 图片识别我**没做**并写清了原因 |
| "如果让你再做一次？" | A-07：修复后必须复验"用户有没有真的感知到"，技术通过不等于用起来了 |

第三行是这张表最值钱的地方——它证明我不是在流水账式地接需求，
而是在区分"技术上修好了"和"用户真的用上了"。

这条区分已经产生过一次实际作用：A-07 在 11/24 标记为"已修待感知"，
11/25 回访确认"缺时刻标签会显示并提示要补时刻"之后才改成"已修"。
如果当时直接按"已修"记账，这条记录就会一直是假的。
