## 一、做法

用同一份正文生成两个载体，避免线上案例页和 PDF 内容漂移：

```
outputs/41_案例正文定稿_2026-11-25.md   ← 文字母本
        │
        ├─→ mvp/case/index.html            ← 在线案例页
        └─→ mvp/case/print/case-pack.html  ← A4 打印版
                    ↓ 无头 Chrome printToPDF
              zhouxu_case_pack.pdf
```

技术路线选的是「HTML 打印样式 → Chrome 生成 PDF」而不是 reportlab 直接绘制，
原因是中文字形：Chrome 会调用系统字体直接绘制字形，reportlab 需要自己嵌字体，
一旦字体子集化出错就会缺字。

## 三、过程中修掉的两个真问题

### 1. 表格被挤成竖排单字

第 8 页的「已知限制」表，两列文字全部竖着排，一列一个字。
根因是我给 `.index td:last-child` 加了 `white-space: nowrap`——
本意是让「断言」那列的数字不换行，结果长文本列被强制不换行，
浏览器只好把第一列压到最小宽度。

改成不设 nowrap 后正常。这类问题在浏览器里看不出来，只有渲染成图才暴露。

### 2. 中文抽取出来是兼容偏旁字（更隐蔽）

生成后用 pypdf 抽字，发现抽出来的是：

> 个⼈项⽬、截⽌时间、冲突并排⽐较

这些是康熙部首区的兼容字符（U+2F00–U+2FD5），长得跟"个人项目"几乎一样，
但搜"个人"搜不到，复制出去也是错的字符。

根因是 Chrome 打印时对 `PingFang SC` / `Hiragino Sans GB` / `Songti SC`
这类 CFF 格式的 macOS 中文字体，退化成了 Type 3 字形，ToUnicode 映射错误。

做了个对照实验（5 种字体 × tagged / untagged 两种打印模式）：

| 字体 | 抽取结果 |
| --- | --- |
| PingFang SC | 苹⽅测试…（偏旁字） |
| Hiragino Sans GB | 冬青⿊测试…（偏旁字） |
| Songti SC | 截⽌时间（偏旁字） |
| Arial Unicode MS | ArialUnicode 测试 未来七天（正常） |
| system-ui | 系统字体测试 紧急程度（正常） |

结论：只有 TrueType（glyf 轮廓）字体能被正确嵌入。
最终字体栈改为 `"Avenir Next", "Arial Unicode MS", "Helvetica Neue", sans-serif`
——拉丁字母走 Avenir Next，中文走 Arial Unicode MS。
等宽栈也补了 Arial Unicode MS，因为 `.kicker` 和 `.card .idx` 里的中文原本会掉回 PingFang。

改完之后：抽取字符 6965，异常字符 0，
「个人」「截止时间」「195」「自动化断言」「冲突并排」全部可搜索。

这个坑值得记：PDF 看起来对，不代表它是对的。
只有把字抽出来搜一遍，才知道别人复制你的链接和文字时会不会出错。

## 四、构建流程

```bash
python3 scripts/build_pdf.py   # 生成 PDF 并渲染 PNG 到 work/pdf/
bash scripts/build_deploy.sh   # 把 PDF 与页面一起放进 docs/
```

`build_pdf.py` 自带三项自检并会打印：

- 页数
- 是否有页面超出 A4（内容溢出会被 `overflow: hidden` 静默截掉）
- 是否有图片没加载成功

## 五、质检

- 逐页渲染成 PNG 人工核对（`work/pdf/page-1.png` … `page-9.png`）
- 9 页均无内容溢出、无未加载图片
- 文本可搜索、可复制
- 隐私：不含学校名、单位名、真实姓名、投递编号
