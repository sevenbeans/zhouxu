## 一、为什么提前做

原排期里案例页结构在 11/29、文案在 12/01、开发在 12/02、上线在 12/03。
这次提前到 11/25，理由是：

1. **11/29 证据冻结后，最难的事就是改口径。** 案例页是口径的载体，
   越晚写，越容易把 11/26 之后新增的内容混进来。
2. **研究记录已经齐了。** 五轮迭代、八个测试套件、两份外部试用反馈，
   现在写出来的每个结论都有出处，不需要再等。
3. **写案例页会暴露研究记录的漏洞。** 写的过程本身是一次审校，
   早写早发现问题，比 12/09 写简历时才发现数字对不上要好。

## 二、页面结构

| 章节 | 内容 | 作用 |
| --- | --- | --- |
| 首屏 | 产品名 + 一句话定位 + 四个硬指标 + 未来七天界面实拍 | 3 秒内说清"这是什么、给谁用" |
| 01 问题 | 三个失效点：日期靠人脑推算、撞车没有决策依据、提醒看到了也不行动 | 把痛点落到具体动作，不讲空话 |
| 02 研究 | 五种方法的样本与产出、唯一被验证的成功标准、"我不说的三句话" | 立住研究口径，不夸大 |
| 03 方案 | 双语义模型（到场型 / 截止型）、三条设计原则、冲突页实拍 | 讲清抽象是怎么来的 |
| 04 迭代 | 五轮迭代，每轮：反馈原文 → 根因 → 改动 → 验证 | 作品的真正价值在这里 |
| 05 验证 | 195 项断言、六个视口、零控制台错误、真实任务记录、外部试用者问题 | 让"验证过"可被检验 |
| 06 边界 | 本期明确不做的六件事、已知限制、下一步 | 主动砍掉的比做出来的更能说明判断力 |
| 07 收尾 | 项目教会我的一件事 + Demo 与源码入口 | 收束到判断力，不收束到功能列表 |

## 三、写作原则

1. **每个结论配一个证据。** 事实来自访谈原话、测试断言或可追溯的记录。
2. **根因优先于现象。** 第五轮写的是"是我覆盖不全，不是用户表达不规范"，
   而不是"修复了中文识别"。
3. **数字必须能追到文件。** 195 = 25 + 20 + 22 + 29 + 32 + 34 + 14 + 19，
   每个数对应一个可运行的测试套件。
4. **主动写失败。** 考公板块被拒绝、导出是快照、识别是长尾问题，
   都写在页面上，而不是藏起来。
