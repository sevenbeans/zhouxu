# 研究收口与 MVP 决策

- 收口日期：2026-11-17
- 证据范围：1 位目标用户的 3 轮文字深访 + 1 次短访谈补充回访
- 决定：停止扩样，进入可运行 MVP 阶段
- 对外表述：定性研究形成方向性判断，不代表已经完成 10 人访谈或市场需求验证

## 1. 停止扩样的理由

现有证据已足够支撑三个方向性判断：

1. 多个招聘、课程和实习节点会让用户失去统一视图。
2. 用户不仅需要日期，还需要具体任务、紧急程度和当前进度。
3. 时间冲突发生时，用户需要岗位上下文，单纯提醒不足以帮助选择。

补充回访没有推翻核心问题，但补充了“无截止日期”“现场已完成”和“冲突需要比较依据”三类边界。继续寻找相似用户带来的边际信息有限，因此停止扩样。

## 2. 本轮研究能支持什么

| 结论 | 证据 | 强度 |
| --- | --- | --- |
| 用户需要未来七天统一视图 | 明确把“未来一周所有规划”作为试用成功标准 | 支持 |
| 每条事项需要具体任务和紧急程度 | 明确列出首屏三项信息 | 支持 |
| 冲突页需要岗位上下文 | 中国移动与农业银行笔试冲突案例 | 支持 |
| 用户希望明确各岗位当前进度 | 明确把任务进度列为试用成功标准 | 支持 |
| 存在无截止日期的招聘流程 | 双选会现场投递 | 支持 |
| 日期错误不可接受 | 前期深访明确表示 | 支持 |
| 投递状态需要人工确认 | 前期深访明确要求 | 支持 |

## 3. 本轮研究不能证明什么

- 不能证明目标用户群普遍存在同样问题。
- 不能证明用户会连续两周上传截图并确认字段。
- 不能证明所有用户都愿意维护“具体任务”和“紧急程度”。
- 不能证明截图 OCR 的准确率已经达到可用水平。
- 不能证明用户会从现有日历或待办工具迁移。
- 不能证明产品已经存在明确付费意愿或市场规模。

## 4. MVP 要验证的唯一核心假设

> 把招聘、课程和实习信息整理成“截止时间 + 具体任务 + 紧急程度 + 当前进度”的未来七天视图，能让学生更清楚地判断本周先做什么，并在时间冲突时做出有依据的选择。

不把“自动识别截图”作为首版唯一成功条件。识别是输入能力，清晰行动计划才是用户结果。

## 5. MVP 最小闭环

```text
上传截图 / 粘贴文本 / 加载示例
→ 形成待确认事项
→ 用户确认日期、任务和状态
→ 进入未来七天视图
→ 发现冲突
→ 并排比较岗位上下文
→ 选择日程处理方式
→ 导出 .ics
```

## 6. 首版必须保留

- 三种日期状态：明确日期、缺失日期、仅发布日期
- 招聘、课程、实习三个分类
- 具体下一步任务
- 紧急程度
- 手动进度状态
- 未来七天视图
- 冲突检测与岗位对比
- `.ics` 导出
- 本地保存，不上传账号

## 7. 首版明确不做

- 自动提交网申
- 自动判断“已投递”
- 自动岗位适配度评分
- 原生 App
- 双向日历同步
- 多用户协作
- 登录、支付和云端数据库
- 没有真实 OCR 时伪造“智能识别已完成”

## 8. 技术与证据边界

首版优先使用本地运行的前端应用：

- 数据存储在浏览器本地
- 支持图片选择并进入待确认流程
- 支持粘贴识别文本或手动录入字段
- 识别模型接入点保留为独立函数
- 未配置模型时显示“待人工确认”，不输出猜测日期
- 导出标准 `.ics`

## 9. 下一阶段验收

### MVP 功能验收

- 能从示例或手动输入创建一个事项
- 能区分明确日期、缺失日期和无需排期
- 能修改具体任务、紧急程度与状态
- 未来七天视图能正确筛选和排序
- 两个同日事项能进入并排比较
- `.ics` 能被日历应用解析

### 试用验收

- 至少 1 名用户完成首次导入
- 至少 1 名用户说出未来七天三项优先任务
- 至少 1 次冲突被正确识别并比较
- 记录每条事项的确认耗时和修改字段

如果无法找到更多试用者，应将项目表述为“基于 1 名目标用户的定性研究与可交互原型”，不得写成“已完成多人验证”。
