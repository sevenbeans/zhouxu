## 2. 这次反馈暴露的产品问题

### 2.1 "预填"和"强制填写"是两件事

第 1 条反馈说明：原文里已经写了"作业"两个字，界面却还让用户从下拉框里选"学校/秋招"。
这不是缺功能，是把系统已经能判断的信息又推回给用户。
修复后，下拉框从"必须选"变成"默认已选好，可以改"，并在旁边说明依据。

### 2.2 文案里带旧日期，比没有文案更糟

第 2 条反馈是本轮最严重的一个。
原文写"下周四"，系统推算 12/3 并把 12/3 写进了"具体下一步"。
用户把日期改成 11/26 后，这句话还停在 12/3——用户看到的和实际排期是矛盾的。
修复方式是把这句话变成**由分类和日期共同生成**，而不是一次性写死。
同时保留一条规则：用户自己动过这句话，系统就不再自动覆盖。

### 2.3 缺时刻的后果必须说出来

第 4 条反馈的实质是：用户不知道"不写时刻"意味着什么。
导出到手机日历时，没有时刻的事项会变成全天事件，也不会参与冲突判定——
也就是说用户以为系统会提醒她"交作业和面试撞车了"，实际上系统根本不知道这两件事撞车。
修复后这个因果链直接写在确认页上，而不是让用户自己踩。

### 2.4 "不是冲突"不等于"不用管"

第 5 条反馈里，用户自己已经意识到"这两个是冲突的"，但系统因为缺时刻没有给出任何提示。
这暴露了原冲突模型的边界：只做"时刻完全相同"的硬判定，漏掉了"同一天、但有一件没写时刻"这个高频中间态。
修复方式是新增软提示区块——不冒充冲突结论，但必须把这两件事并排放出来，
并说清楚"补上时刻后才会给结论"。

## 2.5 补充：手动录入"提交没反应"（同日第三轮反馈）

用户随后反馈"手动录入提交没反应，收件箱也没有"。这不是使用问题，是一个真实的缺陷。

### 根因

`<dialog>` 元素被 `showModal()` 打开后，会进入浏览器的 **top layer**。
top layer 里的元素永远绘制在普通文档流之上，**`z-index` 对它无效**。
而提示条 `#toast` 写在 `<body>` 里、`z-index: 20`，
所以只要弹窗是打开的，任何提示条都会被整块遮住——用户看不到任何反馈。

手动录入路径默认"日期状态 = 明确日期"，但截止日期输入框是空的。
用户填完标题和具体下一步点保存，触发的是"明确日期需要填写截止日期"，
这条提示正好被弹窗挡住。结果就是：**点了没反应、没报错、收件箱也没有。**

同一个缺陷也影响另外两条添加路径——图片方式不选图、文本方式不粘内容，
提示同样看不见，只是这两条更容易被察觉（因为什么都不填更像"忘了"）。

### 修复

1. **提示条按弹窗路由**：弹窗打开时，提示写进弹窗自己的提示条（`.dialog-toast`）；
   弹窗关闭时走原来的全局提示条。
2. **弹窗内提示条改为顶部通栏**（`position: sticky`），随表单滚动始终可见，
   不会被长表单推到屏幕外。
3. **错误落到具体字段**：出错的输入框标红，下方给出字段级说明（`setFieldError`），
   同时把焦点移到出错的框。
4. **手动录入补全字段**：加上进度、紧急程度两个下拉，
   原来这两项只能进确认页再改，录入时就得先选。
5. **日期状态联动**：切到"未找到日期 / 只有发布日期 / 无需排期"时，
   截止日期和时间输入框自动禁用，面板底部同步说明当前状态的后果。
6. **手动录入也查重**：与文本方式同一套规则。

# 第三轮：冲突模型重建（2026-11-25）

- 反馈日期：2026-11-25
- 反馈对象：01 号目标用户（同一名用户，第 3 次反馈）
- 反馈方式：用户在真实使用中口述 1 个问题，主持人事后整理
- 修复版本：`app.js?v=20261125-1`
- 证据边界：仍是 1 名用户的使用反馈，不构成多人验证，也不代表留存

## 1. 反馈原文

> "还有一个，冲突时刻，比如我交作业截止日期是 3 点，但我面试是 2 点半，
> 很可能我 3 点不能结束我的面试，但是这两个事情也不会标记冲突。
> 不可能完全百分百一样的时刻才表示冲突"

## 2. 根因：冲突判定用的是"时刻相等"，不是"时段重叠"

原判定逻辑要求两条事项的时刻**完全相等**才算冲突：

```js
if (one.when.getTime() !== two.when.getTime()) continue;  // 时刻不同就跳过
```

这条规则在两个方向上都是错的：

- **过于宽松**：两件事都占用了同一段真实时间，但因为开始时刻不同，被判成"不冲突"。
- **过于狭窄**：即使时刻不同，只要两件事占用同一时段，依然毫无提示。

用户举的例子精确命中了这个漏洞：作业 15:00 截止、面试 14:30 开始。
按旧逻辑，15:00 ≠ 14:30，两件事"不冲突"。
但按真实时间看，面试的占用时段覆盖了 15:00 那一刻，用户在面试里根本交不了作业。

## 3. 修复：引入"占用时段"模型

判定单位从"时刻点"换成"时段区间"。每条带时刻的事项都算出一个占用时段：

| 事项类型 | 占用时段 | 举例 |
| --- | --- | --- |
| 笔试 / 面试（固定开始） | `[开始时刻, 开始时刻 + 预计时长]` | 面试 14:30 开始，预计 60 分钟 → 14:30–15:30 |
| 作业 / 投递 / 交付（截止型） | `[截止时刻 − 预计投入, 截止时刻]` | 作业 15:00 截止，预计投入 60 分钟 → 14:00–15:00 |
| 当天结束前交（23:59） | 只保留截止这一刻作为卡点 | 避免同一天一堆 23:59 互相误报 |

冲突判定改为两段时段**相交**即冲突：
- 严格相交 → 冲突，重叠多少分钟就是多少
- 时段本身不相交，但一方"截止那一刻"正好落在另一方必须到场的时段里 → 也算冲突（`tight`）

用户的例子因此被正确判为冲突：作业占用 14:00–15:00，面试占用 14:30–15:30，
两段在 14:30–15:00 相交。

### 预计时长从哪来

新增"按类型自动"的默认时长，用户也可以在确认页和手动录入里改：

| 类型 | 默认时长 |
| --- | --- |
| 笔试 | 90 分钟 |
| 面试 | 60 分钟 |
| 课程作业 / 其他截止型 | 60 分钟 |
| 待投递 | 30 分钟 |
| 结果已出 / 已完成 | 15 分钟 |

可选 8 档：15 / 30 / 45 / 60 / 90 / 120 / 180 / 240 分钟，上限 480 分钟。

## 4. 连带的产品决策

### 4.1 冲突分成两档，不再只有"冲突 / 不冲突"

- **硬冲突**：至少有一方是必须本人到场的笔试或面试，需要用户取舍，进并排比较页
- **软冲突（新增）**：时段相交但双方都是可各自完成的截止型事项，不用二选一，
  但要提示"这段时间你排得太满"
- **待判定**：同一天多件事但至少一件没写时刻，并排放着并说明"补上时刻后结论才准确"

### 4.2 冲突信号必须出现在 7 天视图里

原来冲突只在"时间冲突"页出现，用户在一周视图里看不出哪张卡撞车，
必须主动切页才知道。这轮把信号加回卡片：

- 硬冲突 → 红色 `时间冲突` 标签，鼠标悬停显示和谁撞
- 软冲突 → 黄色 `时段排满` 标签
- 每张带时刻的卡片额外显示一行"占用时段"，让用户先看到自己占了哪段时间

### 4.3 修掉一个被新模型暴露的回归

新模型上线后，回归测试发现"同日多件事"软提示整块消失。
根因：11/26 当天有两个 19:00 笔试构成硬冲突，旧逻辑按"整天"排除，
导致当天另外三条缺时刻的事项（含用户真正关心的作业与面试）完全不出现在提示里。

修复：只剔除真正撞车的那几条，其余事项照常进软提示。
这条连坐逻辑本身是上一轮引入的，属于设计缺陷而非编码失误。

## 6. 仍未解决的边界

- 时长是**估算**，不是实测。用户不填就用类型默认值，所以重叠分钟数只是参考。
  真实面试是 45 分钟还是 90 分钟，用户自己最清楚——这也是确认页开放时长选项的原因。
- 跨天的事项仍按"当天日期 + 时刻"处理。23:59 截止的事项在当天 23:59 那一刻才算卡点，
  但如果用户实际拖到第二天才交，系统不会知道。
- 面试的"准备时间"没有被单独建模。一个 14:30 的面试，用户可能 13:00 就在准备了，
  但系统只算 14:30–15:30 这 60 分钟。这是下 12 月的一个候选优化点。
- 仍只有 1 名用户。冲突模型的重构依据是一个人的真实场景 + 两个构造用例，
  不足以宣称这个模型对所有用户都成立。
