# 案例正文（定稿）

**项目**：周序 Zhouxu — 面向求职学生的截止时间管理工具
**类型**：个人产品项目 · 可交互 Web 原型 · 定性研究
**周期**：2026-11-11 至 2026-11-25（研究 4 天，原型 6 天，迭代 7 轮）
**线上**：https://sevenbeans.github.io/zhouxu/ ｜ 案例页：https://sevenbeans.github.io/zhouxu/case/
**冻结时间**：2026-11-25 晚，此后不再加功能、不再改模型

> **口径声明**（放在最前面，因为它约束后面每一句话）
> 本项目的研究对象是 **1 名核心用户**（本人，求职中），另有 **2 位外部试用者**完成跨端走查。
> 因此本文只写：定性研究、可交互原型、单用户任务验证。
> **不写**：市场验证、识别准确率、留存率、效率提升百分比——这些数据一个都没有测过。

## P1 · 一句话说清这个东西

求职学生的截止时间散落在公众号推文、群聊截图、邮件和脑子里。
我做的是把它们收拢成**一页未来七天的行动计划**——
每件事都带**截止时间、具体下一步、紧急程度、当前进度**，
并且坚持一条硬规则：**日期永远由人确认，系统不替用户猜，也不替用户决定要不要写进日历。**

作品：可交互 Web 原型（本地优先，无后端），支持粘贴文本与手动录入，
产出未来七天视图、冲突并排比较与 `.ics` 导出到手机日历。

## P2 · 起点：三个具体的失效点

立项前我访谈了核心用户，问他最近一次从看到招聘信息到完成投递，实际做了什么。
答案里没有"焦虑"这种词，全是动作和缺口：

> "上周，AI 拉取信息，找到网站填网申，提交，等待后续邮箱通知。"

> "都只是记在脑子里，很混乱。"

> "投的秋招太多，会有面试时间冲突的情况，最后只能舍弃一个参加。"

追问下去，失效点收敛成三个，且都能对应到具体动作：

### 失效点一：日期靠人脑推算

看到"周四下午 2 点笔试"，用户得自己算周几、算几号、算还剩几天。
他试过日历和表格，放弃的理由是两句：

> "没有，很麻烦，而且我不知道要怎么导入手机日历。"
> "没找到入口。"

所以问题不只是"没有工具"，而是**工具的入口对他不可见**。

### 失效点二：撞车时没有决策依据

中国移动和农业银行的笔试撞在同一时刻，他"凭感觉"选了一个。
事后他说：

> "根据偏向，但其实我并不知道哪个岗位更适合我。"

他缺的不是提醒，是**并排比较的信息**。系统只能告诉他"你撞了"，
但必须把"为了不撞车，你放弃的是哪个岗位"这件事摆在他面前。

### 失效点三：提醒看到了也不行动

他希望截止前三天和前一天都提醒，也承认"3 天也会忘"。追问原因时他说：

> "看到后没立即行动，可能当时有别的事。"

这句反馈改变了产品方向：需要的不是更多提醒，而是**更早、更集中的一次规划**——
把一周的节点一次性摊开，让人自己决定先做哪个。

## P3 · 研究：样本不大，所以口径很紧

| 方法 | 规模 | 拿到什么 |
| --- | --- | --- |
| 文字深访 | 3 轮 | 最近一次投递的完整还原、信息渠道、记录方式、每步耗时 |
| 补充回访 | 1 次 | 区分"提醒没看到"与"看到后没行动" |
| 真实任务测试 | 1 名用户 1 次 | 首次导入、七日视图理解、冲突比较，含确认耗时与修改字段 |
| 跨端走查 | 2 位外部试用者 | iOS 与桌面各一轮，暴露导出、图文识别、字段可理解性问题 |
| 样本集 | 6 张公开截图 | 标注日期原文与唯一判断规则，分明确 / 只有发布日期 / 未找到日期三类 |

### 唯一被明确验证的成功标准

试用结束时用户自己给验收话术：

> "我能明确知道未来一周的所有规划。"

这句话后来成了周视图的验收基准，而不是我自拟的功能清单。

### 样本集里最重要的一条规则

样本里有三种日期状态，处理方式必须不同：

| 状态 | 判断规则 | 处理 |
| --- | --- | --- |
| 明确日期 | 原文出现截止日期 | 进入七日视图 |
| 只有发布日期 | 原文只有"发布于 XX" | **不当作截止日**，标为"只有发布日期" |
| 未找到日期 | 可见区域没有日期 | 不编造，标"未找到日期"并给出回源动作 |

还有一条边界样本：某岗位页写着"毕业时间 2027 年，招聘截止 2026.12.31"。
**毕业年份不是截止日期**——这是专门为拦住"看起来像日期的日期"设计的样本。

### 我不说的三句话

- 不说"经过市场验证"：没有做过多用户定量调研。
- 不说"识别准确率 X%"：本期根本没有视觉模型。
- 不说"效率提升 X%"：没有做过对照实验。

## P4 · 方案（一）：核心决定——先分清"要人到场"和"要交东西"

第一版我把所有时刻都当成"截止时间"。结果用户输入
"明天晚上 8 点腾讯会议汇报 5002"，20:00 被填进了"截止时间"字段。

**根因是我按事项叫什么判断语义。** 我维护了一张固定状态列表 `["exam", "interview"]`，
凡是里面的就算"要人到场"，会议不在里面，于是被当成"要交东西"。

改正后的模型不问事项叫什么，只问一件事：**这件事是不是要求人到场。**

| | 要人到场 | 要交东西 |
| --- | --- | --- |
| 登记什么 | **开始时刻**，可选真实结束时刻 | **截止时刻**，前面不铺准备窗口 |
| 占用形态 | 一段区间 `[开始, 开始 + 时长]` | 一个时点 `[DDL, DDL]` |
| 典型事项 | 笔试、面试、会议、答辩、宣讲、组会 | 网申、课程作业、实习交付、报名截止 |
| 结束时间缺失时 | 按类型估算，界面明确标注"（估算）" | 不涉及 |

### 为什么这个模型值得做

改成这个模型之后，考公场景**零成本接入**——报名的 DDL、笔试的开始时刻、
体检政审的日期型节点，全都落在已有规则里，不需要第二套逻辑。

考公词也优先于通用词："国考笔试"必须归考公，不能归秋招。

### 冲突判定：三条规则，而不是"时刻相等"

用户给过我一条很精确的纠错：

> "首先关于面试，考试这种，一般登记都是开始时间，然后你再往后推时间，前面的准备时间就不用算进去了。
> 然后交作业，实习交付，记的是 ddl，也是只用登记最后时刻就行，前面的提醒就不用了。再这个基础上再去算冲突事件。"

最终判定规则是三条：

1. 两个占用区间相交
2. 一个截止时点落在另一个的占用区间里
3. 两个截止时点落在同一时刻

界面上的表述也跟着人话走。冲突标题不是"2 个冲突"，
而是 **"11/26 周四 · 15:00 落在 14:30–15:30 里"**，并解释一句：
"截止时刻落在必须到场的时段里，来不及做完，需要决定"。

## P5 · 方案（二）：三条不妥协的设计原则

### 原则一：日期永远人工确认

原始信息与确认结果并排展示，日期不会静默猜测。
用户输入"周四产品经理面试"，界面给的是：

> **原文依据**：周四产品经理面试
> **日期推算依据**：原文只写了周四，按本周周四计算，若当天已过则顺延到下周（原文匹配「周四」）
> 这是按原文推算的结果，请确认是否正确。

并且**推算依据和用户手改的日期同时保留**：
用户把 12/3 改成 11/26，界面会写明"你已手动改为 11/26 周四，原文推算的是 12/3 周四"。

### 原则二：缺信息就说缺信息

截止日期缺失就标"未找到日期"；只有发布日期就明说只有发布日期；
结束时间没填就写"结束时间没填，按 60 分钟估算"；
截图上传明确写"本版本不会自动识别图片文字"，并给出"截图 → 长按复制文字 → 粘贴"的替代路径。

**用户反馈里最贵的成本就是"我以为它能"。**

### 原则三：本地优先，不上传

数据只存在本机浏览器，可一键清空。
求职场景涉及公司与个人隐私，"数据不出本机"本身就是产品承诺，
而不是技术妥协的借口。

## P6 · 迭代：七轮，每一轮都推翻了一条我以为对的规则

累计 7 轮反馈迭代，其中 5 轮集中在 11 月 25 日一天之内。
完整台账见 `40_反馈台账_2026-11-25.md`（24 条，逐条含原话、根因、处理、验证用例）。

### 更早的两轮（11/24）

**第一轮（六条一起改）**：粘贴"交作业"后分类仍要手选、"具体下一步"留着旧日期、
裸星期"周四"推算不出、缺时刻没有任何提示、重复提交无去重无删除、同日缺时刻不提示冲突。

其中最严重的是第二条：用户把日期从 12/3 改成 11/26，
"具体下一步"还写着"核对推算日期 12/3 周四"——
**界面上的话和实际排期矛盾，比没有话更糟。**
修法是让这句话由分类与日期共同生成，且用户自己改过就不再自动覆盖。

**第二轮（一个真实缺陷）**：用户反馈"手动录入提交没反应，收件箱也没有"。
根因不是逻辑错，是 `<dialog>` 进入浏览器 **top layer**，
`z-index` 对它无效，错误提示被整块遮住——
用户点保存、触发校验、提示出现在被遮住的位置，于是表现为"点了没反应"。
修法：提示条按弹窗路由、弹窗内改顶部通栏、错误落到具体字段并标红、焦点移到出错框。

### 11/25 的五轮

**第一轮 · 导出到手机日历比想象中难**
iPhone 用户反馈下载的 `.ics` 导不进日历，日历里没有导入入口。
一半是 iOS 日历本身没有导入按钮，一半是我的 ICS 不合 RFC 5545
（`DTSTAMP` 用了本地时间、超长行没折行、文件名是中文，iOS 对非 ASCII 文件名的 .ics 识别不稳定）。
改法：按 RFC 标准化、补「分享给我自己」兜底、导出后给平台化指引，
并在指引里点明那句关键澄清：**日历 App 本身没有"导入"按钮**。

**第二轮 · 试用者建议加考公板块，我拒绝了**
建议值得接，但不做板块。做成独立板块意味着考公要有自己的时间轴、提醒规则和冲突口径，
等于在交付前再造一个产品；更关键的是，
**做成板块等于承认"我的抽象只是秋招规则换了个名字"**。
最终只加第四个分类。顺带被新写的测试用例撞出一个老 bug："实验报告"被误判为实习。

**第三轮 · 公告写明的结束时间是事实，不是估算**
用户问："考试这个事物，为什么只会有一个截止日期，考试也是有时间的。"
原来笔试面试的时长是系统猜的（笔试 90 分钟、面试 60 分钟）——
而考公笔试的 9:00–11:00 是公告写明的**已知事实**。
加真实结束时间字段，填了就不再显示时长下拉（那是两个会互相矛盾的答案）。
连带修掉一个真 bug：导出的 `DTEND` 一直是硬编码 +1 小时，
界面写着 11:00、日历里却是 10:30。

**第四轮 · 我按名字判语义，用户按事情判语义**
"明天晚上 8 点腾讯会议汇报 5002"的 20:00 被填进"截止时间"。
根因就是那张固定状态列表。改成按到场语义判定后，
会议、宣讲、答辩、双选会、组会全部自动走同一套逻辑；
会议号 5002 从标题剥离到"补充说明：会议号/房间号"。

**第五轮 · "要写数字才能识别"不是用户不规范，是我覆盖不全**
试用者反馈"下个月 3 号""两天后""三天后"都识别不了。
原来只覆盖阿拉伯数字与固定词，漏掉了中文里最常见的两种写法。
补中文数字转换（到九十九）、中文相对天数、带前缀月日（本月 / 下个月 / 月底）。
其中"3 天内"按最后一天计算，并在依据里写明原因。

### 这一轮之后我决定冻结

五轮下来，剩余问题都是长尾表达，不是结构缺失。
**继续改会稀释作品集的说服力**——取舍链条在第四轮就已成型。
于是 11/25 晚冻结：不再加功能、不再改模型，新问题只记录不修。

## P7 · 验证：怎么证明它没坏

### 冻结当天跑完的基线

**195 项自动化断言全部通过**，8 个套件：

| 套件 | 覆盖 | 断言 |
| --- | --- | ---: |
| 中文日期 | 中文数字相对天数、带前缀月日、标题清理 | 25 |
| 会议 | 会议类事项、冒号分钟、会议号剥离 | 20 |
| 结束时间 | 真实起止、估算标注、导出 DTEND | 22 |
| 冲突 | 区间重叠、截止落入场段、软冲突升级 | 29 |
| 反馈 | 分类预填、缺时刻提示、查重与删除 | 32 |
| 手动录入 | 三种添加方式的报错可见性 | 34 |
| 考公 | 第四分类的识别、优先级与导出 | 14 |
| iOS 修复 | iPhone 导出、分享兜底、图片选择 | 19 |

另有六个视口（360 / 390 / 768 / 900 / 1180 / 1440）排版无横向滚动、无元素越界，
控制台零错误。报告与截图存于 `work/qa/`。

### 真实任务测试记录了什么

| 观察点 | 用户的回答 |
| --- | --- |
| 首次导入到未来七天视图 | 用时不到一分钟，状态修改可用 |
| 周视图能否一眼看出要做什么 | "可以" |
| 推算日期标签是否看懂 | "大部分可以" |
| 缺时刻提示有没有真的被感知 | 复访确认：会显示，并明确提示要补时刻 |
| 发现的偏差 | 以为导出后会自动同步，实际是快照 |

### 外部试用者带回来的问题

| 反馈 | 处理 |
| --- | --- |
| iPhone 导不进日历 | ICS 标准化 +「分享给我自己」兜底 + 平台化指引 |
| iPhone 选不了图片 | input 改视觉隐藏，由 `<label>` 原生触发 |
| 电脑端图片无法识别日期 | 本期明确不做，界面诚实降级并给替代路径 |
| 同一天不按紧急度排 | 同一天按紧急程度降序，同紧急度再按时刻 |
| 字段看不懂（"具体下一步""岗位上下文"） | 字段白话化 + 次要字段折叠 |

### 一个关于"修好了"的教训

"缺时刻"提示在 11/24 就修完了，测试也是全绿的。
但我在台账里没有直接记"已修"，而是记成**"已修待感知"**——
因为用户第二天还在提这件事。
11/25 回访确认"标签会显示并明确提示要补时刻"之后，才改成"已修"。

**测试通过说明代码没坏，只有回访能说明用户用上了。**
把两者混为一谈，这条记录就会一直是假的。

## P8 · 边界：这个产品明确不做什么

下面每一条都是**主动砍掉的**，不是做不出来。

| 不做 | 理由 |
| --- | --- |
| 真实 OCR / 视觉模型 | 没有可信的准确率就不能承诺；本期把"做不到"说清楚 |
| 自动提交网申 | 涉及第三方账号与授权，风险与收益不成正比 |
| 岗位适配度评分 | 没有可靠依据，评分会让用户误以为决策被替代 |
| 多人账号、云端数据库 | 会推翻本地优先的隐私承诺 |
| 双向日历同步 | 导出是快照，同步要做冲突合并，超出当前规模 |
| 考公独立板块 | 会否定自己的抽象；只加分类 |
| 原生 App、多人试用 | 交付前不做；研究样本也只有 1 名核心用户 |

### 已知限制与遗留

- 导出是快照，不会自动同步（界面已加常驻说明）
- 结束时间缺失时按类型估算（界面标注"（估算）"）
- 截图上传不做识别（本期明确不做）
- 中文日期长尾表达仍可能漏（冻结期只记录）
- 查重按"归一化标题 + 同一天"，"周报"这类周期性事项仍需用户自己判断
- 分类与进度是关键词匹配，"数据分析报告"可能被判成实习——这是有意的取舍：
  **宁可让用户改一次，也不要系统猜错分类后悄悄归错位置。**

## P9 · 复盘：这个项目教会我的一件事

一开始我以为这个产品是"把招聘信息整理进日历"。
做到后面才发现，真正的难点从来不是日历，
而是在**信息缺失、时间模糊、语义不清的时候，不替用户做决定，但也不让用户两手空空**。

具体到三个转变：

**第一，从"识别得多准"转向"缺信息时怎么说"。**
真正让用户信任的不是识别率，而是"我没找到日期"这句话说得足够清楚。

**第二，从"功能多"转向"抽象对"。**
考公板块被拒绝那一次，是这个项目里最重要的决策。
如果考公需要另一套规则，说明我的抽象是假的。

**第三，从"修完了"转向"被用上了"。**
七轮迭代、24 条反馈里，有一类问题始终不是技术问题：
用户看到了吗？看懂了吗？行动了吗？
这些只能靠回访回答，不能靠测试回答。

所以最后它只有一条硬规则：

> **系统负责把话听清楚、把不确定性摆出来，把"写不写进日历"这件事永远留给用户。**
